# PB-06 – PB-08 Accounts: register, sign in / out, passwords

Sprint 1 · stories · 3 + 3 + 2 points · traces to FR1, NFR1, IR 1.8 · GitHub issues #6, #7, #8

Built as one item because the three stories share one account system (one set of routes,
one password rule, one session). See `docs/decisions.md`, 11 Nov 2026.

## What was built

A complete, hand-written account system on Laravel's session authentication, with React pages
rendered through Inertia. No starter kit or Fortify (PB-02 decision).

- **Register (PB-06):** name, email, password and role (borrower or investor). The account is
  saved as `pending_verification`, the user is signed in and lands on their role's portal,
  which shows a "pending verification" notice while that status lasts.
- **Sign in / out (PB-07):** sign-in redirects to the borrower, investor or admin portal.
  Five failed attempts for one email from one IP address lock sign-in for 60 seconds. Sign-out
  destroys the session and the CSRF token.
- **Role gate (PB-07):** a `role` middleware returns 403 Forbidden when a signed-in user opens
  another role's portal. Guests are sent to sign in.
- **Passwords (PB-08):** forgot password emails a reset link (written to the log in
  development), links expire after 60 minutes and work only once, and signed-in users can
  change their password by giving the current one.
- **One password rule** for register, reset and change: at least 8 characters, upper- and
  lower-case letters, a number and a symbol (`Password::defaults()`).
- **Placeholder portals** at `/borrower`, `/investor` and `/admin`. Later items fill them in.
- **Demo accounts** in the seeder, one per role (`borrower@example.com`,
  `investor@example.com`, `admin@example.com`, password `Demo#2026`). The seeder is the only
  way to create an admin; the public form never offers that role.
- **101 new tests** (205 in the web suite, up from 104).

## Design decisions and alternatives

1. **Hand-written, not Fortify or a starter kit.** Fortify would supply the controllers and
   rate limiting in a few lines of config, but the logic would sit in a vendor package that
   would still have to be explained in the viva. Each piece here is a small class in `app/`.
   The parts that *are* framework-provided are the standard building blocks: the session guard
   (`Auth::attempt`), the password broker (reset tokens) and `RateLimiter`.
2. **Role gate as route middleware, not checks inside controllers.** Each portal is a route
   group with `->middleware(['auth', 'role:investor'])`, so every route a later item adds
   inside the group is gated automatically. *Alternative:* Laravel policies/gates per action.
   Those are still needed later for record-level rules ("only the owner of this campaign"),
   but whole-portal access is one rule per role and belongs on the route. A test walks every
   application route and fails if any non-public route is missing `auth`, or a portal route is
   missing its role, so a forgotten gate is caught in CI.
3. **403, not a redirect, for the wrong role.** A signed-in user opening another portal is not
   lost: they are forbidden. 403 states that plainly, and the tests can assert it exactly.
4. **`role_id` set by the controller, not the form.** `role_id` and `status` are not
   mass-assignable (PB-05). The form sends a role *name*, validated against
   `borrower`/`investor` only, and the controller looks up its id. Adding `role_id=3` or
   `status=verified` to the request does nothing (tested).
5. **Sign-in rate limit keyed by email + IP.** Keyed by IP alone, one office or mobile network
   shares a counter; keyed by email alone, an attacker could lock any user out from anywhere.
   Email + IP limits password guessing per account per address. The lock is 5 attempts per
   60 seconds, and a successful sign-in clears the counter.
6. **No account enumeration.** Sign-in says "These details do not match our records" for both
   an unknown email and a wrong password, and forgot password gives the same answer whether
   or not the email is registered (and sends nothing if it isn't). Otherwise these forms would
   tell an attacker which emails have accounts. Register is the exception: it must say the
   email is taken, which is the usual accepted trade-off.
7. **Pending users can sign in.** Verification happens *after* the user completes their profile
   and KYC upload (PB-09/PB-10), so a pending user must be able to sign in. The pending status
   restricts what they can do in later items; here it shows a notice.
8. **`Password::defaults()` without `uncompromised()`.** `uncompromised()` checks the password
   against the Have I Been Pwned API. That would make registration and every CI run depend on
   an outside service being reachable. Noted as a production improvement.
9. **Validation on the server only (`noValidate` on forms).** The browser's built-in messages
   differ between browsers and can be bypassed. All rules live in Form Requests and every
   message the user sees comes from the server, so the tests check exactly what users see.
   The password hint under the field tells the user the rule before they submit.
10. **Session regenerated on sign-in, invalidated on sign-out.** A new session id after sign-in
    blocks session fixation, and invalidating the session plus a new CSRF token on sign-out
    makes the old session cookie useless.

## Sample code

The role gate: a route group per portal, and the middleware it uses.

```php
// web/routes/web.php
Route::middleware(['auth', 'role:'.Role::INVESTOR])->prefix('investor')->name('investor.')->group(function () {
    Route::get('/', [PortalController::class, 'investor'])->name('portal');
});

// web/app/Http/Middleware/EnsureUserHasRole.php
public function handle(Request $request, Closure $next, string $role): Response
{
    // 403 Forbidden rather than a redirect: the user is signed in, they just aren't
    // allowed here, and a 403 is what the role-access tests check for.
    abort_unless($request->user()?->hasRole($role), 403);

    return $next($request);
}
```

Sign-in with rate limiting (`LoginRequest`):

```php
public function authenticate(): void
{
    $this->ensureIsNotRateLimited();

    if (! Auth::attempt($this->only('email', 'password'), $this->boolean('remember'))) {
        // Count the failure. After MAX_ATTEMPTS the key is locked for DECAY_SECONDS.
        RateLimiter::hit($this->throttleKey(), self::DECAY_SECONDS);

        // One message for "no such email" and "wrong password", so the form can't be used
        // to find out which emails have accounts.
        throw ValidationException::withMessages([
            'email' => 'These details do not match our records.',
        ]);
    }

    RateLimiter::clear($this->throttleKey());
}

private function throttleKey(): string
{
    return Str::transliterate(Str::lower($this->string('email')).'|'.$this->ip());
}
```

### Checking that the tests can fail

Two deliberate breakages, each reverted afterwards: removing `role:investor` from the
investor route group made 5 tests fail (TC-LOG-17 ×2, TC-LOG-18, TC-LOG-23), and disabling
`ensureIsNotRateLimited()` made TC-LOG-10 fail.
