# PB-18 – PB-20 Simulated wallet, pledging and all-or-nothing settlement

Sprint 4 · stories · 5 + 5 + 5 points · traces to IR 1.5, NFR1, FR6 · GitHub issues #18, #19, #20

Built as one item: pledging (PB-19) is a wallet transfer (PB-18), and settlement (PB-20) is the
refund or funding of those pledges, so all three share one ledger, one set of locks and one
reconciliation check. See `docs/decisions.md`, 25 Nov 2026.

Screenshots for the report are taken once in Sprint 5 (PB-56), so there are none here.

## What was built

### PB-18 Simulated wallet and ledger

- **Double entry for every money movement.** `WalletLedger::transfer()` writes one debit and one
  credit of the same amount, sharing a `transfer_ref`, in one database transaction. It is the
  only code that writes `wallet_transactions`.
- **An "external" account for the outside world.** It stands in for a bank, so top-ups and
  withdrawals are pairs too. It is the one account allowed below zero, which the database
  enforces with three things:
  - a `wallet_type` column on every entry;
  - a composite foreign key `(wallet_account_id, wallet_type)`, so the column must match the
    entry's real account;
  - a CHECK `wallet_type = 'external' OR balance_after >= 0`.
- **No stored balance.** A wallet's balance is its latest entry's `balance_after`, and the
  reconciliation check proves that equals the sum of all its entries.
- **Locks.** Both accounts are locked (`lockForUpdate`) in id order before their balances are read,
  and balances are read with a locking read.
- **`php artisan wallet:reconcile`** (`LedgerReconciler`) checks six things:
  1. every transfer is exactly one debit and one credit of the same amount;
  2. each account's chain of balances is unbroken;
  3. no user or escrow wallet is ever below zero;
  4. all accounts together sum to zero (money is only moved);
  5. each escrow holds exactly its campaign's held pledges;
  6. every pledge's transfers match its status.
- **Wallet page** for investors and borrowers:
  - `WalletCard` with the balance (counting up), the money held in pledges, Top up and Withdraw,
    and "Simulated wallet, no real money.";
  - the top-up and withdraw dialogs;
  - the full history with the shared search-and-filter bar and pages.
- **Who can move money.** Only verified accounts (the `move-money` gate).
- **Limits.** Top-ups MVR 10 to 1,000,000 at a time; withdrawals MVR 1 up to the balance.

### PB-19 Pledge to a campaign from the wallet

- **Route.** `POST /investor/campaigns/{campaign}/pledges`, protected by `can:pledge,campaign`.
  The existing gate covers a verified investor, the risk acknowledgement, the campaign being open,
  and Shariah-only mode.
- **Validation** with a clear message for each rule:
  - at least MVR 100 (or the remaining amount, if less);
  - no more than the remaining amount;
  - no more than the wallet balance.
- **`PledgeService` runs it all in one transaction:**
  1. lock the **campaign row** first, so pledges to one campaign run one at a time;
  2. check the gate and the remaining amount again;
  3. create the held pledge;
  4. transfer from the investor's wallet into the campaign's escrow.

  When two investors pledge the last amount at the same moment, the second waits for the lock,
  then sees nothing left and is refused.
- **On the campaign page:**
  - the pledge panel shows your balance, the amount left to raise and your own pledges;
  - the amount is checked as you type;
  - a `ConfirmDialog` shows the amount, where the money goes and what happens if the campaign
    isn't funded, with "Simulated wallet, no real money.".

  Several campaigns, and several pledges to one, are allowed.

### PB-20 Funding progress and all-or-nothing settlement

- **Progress updates after each pledge,** on:
  - the marketplace cards;
  - the campaign page's funding ring;
  - the borrower's request page (new funding card).
- **Funded immediately.** The pledge that reaches the target marks the campaign funded, in the
  same transaction. The money stays in escrow, with pledges held, until disbursement (PB-34).
- **The deadline job.** `campaigns:settle-deadlines` is scheduled every minute. Each live campaign
  past its deadline is settled in its own transaction, locking the campaign first:
  - if the target was reached, it is funded;
  - otherwise it is marked not funded (`failed`), and every held pledge is refunded from escrow
    to its investor and marked refunded.

  Running it again changes nothing.
- **Notifications** (`FundingOutcome`), by email and stored in the database, sent after the money
  has moved:
  - funded: the borrower and each investor, with the investor's own total;
  - not funded: the borrower;
  - refunded: each investor, with their refund.

  The wording is safe for Shariah campaigns, and every message says the money is simulated.
- **Locally,** `composer run dev` also starts the scheduler (`schedule:work`). `web/README.md`
  documents running the job by hand and the two demo campaigns that close 5 and 10 minutes after
  seeding.

## Design decisions and alternatives

- **An external account rather than single-entry top-ups.** Every movement is a pair, so the
  ledger is provably balanced: all accounts sum to zero.
- **Balances derived, not stored.** A stored balance can drift from the entries. Here the latest
  `balance_after` is the balance, and the reconciliation check proves it.
- **READ COMMITTED plus explicit row locks.** The concurrency tests found a real double spend under
  MySQL's default REPEATABLE READ:
  - a transaction's view of the data is fixed at its first plain read, which happened before it
    waited for the wallet lock;
  - so after the first withdrawal committed, the second still saw the old balance and paid out
    again.

  REPEATABLE READ's gap locks also made pledges to *different* campaigns block each other. Money
  transactions now run at READ COMMITTED, where every read sees the latest committed data and
  locks cover only the rows touched. The order is fixed by locking the campaign, then the wallets
  in id order, so nothing can deadlock.
- **Funded at the moment the target is reached.** This is all or nothing without waiting for the
  deadline, and the job still covers any campaign left live with its target met.
- **A one-minute scheduled job rather than a delayed job per campaign.** It is simple, idempotent,
  and survives a restart.

## Sample code

The core of every money movement (`web/app/Services/WalletLedger.php`):

```php
return self::run(function () use ($from, $to, $cents, $type, $pledge, $description) {
    // Lock both rows, lowest id first, before reading either balance.
    WalletAccount::whereKey([$from->id, $to->id])->orderBy('id')->lockForUpdate()->get();

    $fromBalance = $this->lockedBalance($from);
    if (! $from->isExternal() && $fromBalance < $cents) {
        throw new InsufficientFunds('Not enough money in the wallet for '.Money::format($cents).'.');
    }
    $toBalance = $this->lockedBalance($to);

    $ref = (string) Str::uuid();
    $this->entry($from, $ref, $type, WalletTransaction::DEBIT, $cents, $fromBalance - $cents, $pledge, $description);
    $this->entry($to, $ref, $type, WalletTransaction::CREDIT, $cents, $toBalance + $cents, $pledge, $description);

    return $ref;
});
```

## How the concurrency tests work

Each worker is a separate PHP process with its own MySQL connection (`tests/Concurrency/worker.php`).
The test is deterministic rather than relying on timing luck:

1. The test locks the row the workers will compete for: the campaign, or a wallet.
2. It starts the workers. Each prints its connection id, then blocks on that lock.
3. The test polls `SHOW FULL PROCESSLIST` until **every** worker is waiting inside a locking
   statement on that table.
4. Only then does it release the lock, so they genuinely contend.

Every wait has a fixed timeout. `tearDown` stops the workers and deletes every row the test
created. The four tests take about 2 seconds, and passed 10 runs in a row locally.
