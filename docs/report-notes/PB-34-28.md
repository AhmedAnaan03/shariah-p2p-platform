# PB-34 + PB-28 Disbursement, repayment schedules and the Murabahah contract

Sprint 4 · stories · 5 + 5 points · traces to FR11, FR8, IR 2.2.5 · GitHub issues #34, #28

Built as one item: a Murabahah's deferred payment schedule (PB-28) only exists once a funded
campaign is paid out and its schedule generated (PB-34). See `docs/decisions.md`, 26 Nov 2026.

Screenshots for the report are taken once in Sprint 5 (PB-56), so there are none here.

## What was built

### PB-34 Disbursement and repayment schedule generation

- **Payout when funded.** `DisbursementService::disburse()` runs straight after the pledge that
  completes a campaign, and every minute in `campaigns:settle-deadlines` for any campaign still
  `funded`. In one transaction that locks the campaign row first, it:
  1. locks the held pledges and checks they add up to the target;
  2. pays the whole escrow to the borrower's wallet as **one** `disbursement` transfer (one debit,
     one credit, shared `transfer_ref`), so the escrow is back to zero;
  3. marks every pledge `settled`;
  4. writes the schedule (`ScheduleGenerator`);
  5. sets the campaign to `repaying` with `disbursed_at`, and writes an audit log entry.

  Running it twice changes nothing. It runs in its own transaction after the pledge has committed,
  so a payout problem is logged and retried by the job instead of undoing the investor's pledge.
- **Schedules per contract**, in whole cents, first due date one month after the payout:
  - *Conventional:* amortised monthly instalments from the yearly rate; interest on the balance
    still owed; the last instalment repays exactly what is left.
  - *Murabahah:* (cost + markup) ÷ tenure, equal instalments, the leftover laari on the last.
  - *Mudarabah:* planned capital returns only, `return_due` NULL (see below).
- **Investors' shares.** `InstalmentSplit` splits each row between investors in proportion to
  their pledges (largest remainder), capital and return separately, always adding up exactly.
- **Reconciliation.** `LedgerReconciler` rule 7: every paid-out campaign has exactly one payout,
  from its own escrow to its own borrower, equal to its settled pledges, and settled pledges never
  exist without one. With rule 5 this proves the escrow is zero. `wallet:reconcile` passes.
- **Notifications.** `CampaignDisbursed` (database and email) replaces PB-20's "fully funded"
  email: the borrower gets the amount paid in and the first row; each investor their pledged total
  and their share of the first row. "Not funded" and "refunded" are unchanged.
- **Pages.**
  - Borrower's request page: a summary, the months as a `RepaymentScheduleChart` (stacked capital
    and return, Recharts) in a `ChartFrame` (title, takeaway, legend, "View as table"), and a
    `RepaymentTimeline` of every row.
  - Investor's campaign page: the schedule as a table with "Your share" of every row, what they
    invested, their percentage and their share in total.
  - The wallet history links a disbursement to the request it paid out.
- **Demo time tool (local only).** Admin → Demo controls (`/admin/demo`) and
  `php artisan demo:advance-schedule {campaign} {--overdue=}` move every unpaid row of a schedule
  by the same number of days, so the next row is due today or N days ago. Labelled as a demo tool;
  the routes exist only when `APP_ENV=local`, and the command refuses to run anywhere else.
- **Demo data.** The seeder adds two paid-out campaigns: sme@example.com's Murabahah "Laundry
  machines for the guest house" and borrower@example.com's Mudarabah "Food truck for Malé
  evenings", both part-funded by investor@example.com.

### PB-28 Murabahah contract template

- **Asset cost and a disclosed, fixed markup, with no interest-rate field** was built in PB-13: the
  request form asks for the asset, its cost and the markup, and the database CHECK
  `campaigns_murabahah_terms_check` (with `campaigns_conventional_terms_check`) makes an interest
  rate on a Murabahah impossible to store.
- **Deferred payment schedule derived from cost + markup:** `ScheduleGenerator::murabahah()`
  splits the sale price into equal monthly instalments and divides each into capital and markup
  in proportion, so the markup adds up to the agreed markup and the capital to the asset cost.
- **Markup cannot change after the contract is agreed:** an `updating` event on `Campaign`
  refuses any change to the markup (and the cost, tenure, contract type and other terms) once
  `funded_at` is stored, throwing `ContractRuleViolation`.

### Mudarabah: a planned capital return schedule, not a debt

Decided with the developer during planning:

- The rows are called **"Planned capital return"** everywhere: the database column comments, the
  timeline, the chart, the investor's table and the emails. They are never called an instalment,
  "due" or "owed".
- A passed date shows **"Planned date passed, awaiting business report"**, never "late". The status
  badge reads "Returning capital", and the rows don't count in a borrower's repayment record.
- Everyone is told that capital is returned according to the business's results, and that in a
  genuine business loss investors bear the loss of capital in proportion to their share, except
  in cases of negligence or misconduct.
- Profit distribution, loss allocation and the final settlement of capital are PB-29's, as noted
  on issue #29.

## Design decisions and alternatives

| Decision | Alternatives | Why |
|---|---|---|
| Payout in its own transaction right after funding, the job as backstop | Inside the pledge's transaction; only in the job | A payout bug can't undo a pledge; one code path for both triggers; the pause in `funded` is a moment |
| One payout email instead of "funded" + "paid out" | Keep both | They would arrive seconds apart, and the old one said the money stays in escrow |
| Whole cents, last row takes the rounding | Floats; spread the cents | Totals are exact and easy to show in a test table |
| Murabahah: split the sale price first, then markup in proportion | Split cost and markup each by the tenure | Equal instalments (MVR 4,500.00, not 4,499.99) are what "(cost + markup) ÷ tenure" means to a borrower |
| Due dates counted from the payout, end-of-month clamp | Chain from the previous date | Chaining drifts: 31 Jan → 28 Feb → 28 Mar |
| Shares split capital and return separately | Split the instalment total | PB-35 pays capital and return as separate entries |
| Markup lock as a model event | MySQL trigger; controller check | A CHECK can't compare with the stored row; a trigger hides the rule from PHP and its tests |
| Demo tool moves rows, not the clock | Fake "now" app-wide; seed overdue rows | Other dates in the app stay true; only the chosen campaign changes |

## Code excerpt (for the sample code section)

`app/Support/ScheduleGenerator.php`: a Murabahah's sale price in equal instalments, each divided
into capital and markup, adding up exactly.

```php
public static function murabahah(int $cost, int $markup, int $months): array
{
    self::assertValid($markup, $months);
    $instalments = self::evenSplit($cost + $markup, $months);
    if ($cost + $markup === 0) {
        return [$instalments, $instalments];
    }

    // Each instalment's share of the markup, in proportion to its size, adding up exactly.
    $markups = array_values(InstalmentSplit::shares($markup, $instalments));
    $capital = array_map(fn (int $instalment, int $part) => $instalment - $part, $instalments, $markups);

    return [$capital, $markups];
}

public static function evenSplit(int $total, int $parts): array
{
    self::assertValid($total, $parts);
    $each = intdiv($total, $parts);
    $split = array_fill(0, $parts, $each);
    $split[$parts - 1] = $total - $each * ($parts - 1);

    return $split;
}
```
