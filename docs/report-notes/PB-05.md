# PB-05 Core data model and migrations

Sprint 1 · chore · 5 points · traces to IR 1.8, Table 13 · GitHub issue #5

## What was built

The platform's core MySQL schema: 14 tables, their foreign keys, NOT NULL rules and CHECK
constraints, built by Laravel migrations that all roll back cleanly. The schema follows the ERD
in [`docs/erd.md`](../erd.md), which was drafted first and approved before any migration was
written. One Eloquent model per table (except `notifications`, which uses Laravel's built-in
`DatabaseNotification`) holds the relationships, casts and one model-level rule.

- **Tables:** `roles`, `users` (extended), `borrower_profiles`, `investor_profiles`,
  `kyc_documents`, `campaigns`, `pledges`, `wallet_accounts`, `wallet_transactions`,
  `repayment_schedules`, `repayments`, `risk_scores`, `notifications`, `audit_logs`.
- **17 foreign keys**, all `ON DELETE RESTRICT`.
- **14 CHECK constraints** enforced by MySQL itself, including the Shariah rule that no
  Murabahah or Mudarabah campaign can ever store an interest rate.
- **One model rule** the database can't check: a Mudarabah instalment never has a
  predetermined return.
- **Encrypted national ID numbers** on both profile tables.
- **Factories** for users (with `borrower()`, `investor()`, `admin()`, `verified()` states),
  borrower and investor profiles, and campaigns (`conventional()`, `murabahah()`, `mudarabah()`).
- **90 new tests** (98 in the web suite, up from 8), including one that compares the live schema
  column-by-column with the ERD and one that rolls every migration back step by step.

## Design decisions and alternatives

1. **ERD first, approved before migrations.** The table list, columns and relationships were
   reviewed as a list and a Mermaid diagram, then four changes were made before any code:
   `return_due` nullable for Mudarabah, two-way contract CHECKs, encrypted national IDs, and
   return payouts tracing to both pledge and repayment.
2. **One role per user (`users.role_id`)** instead of a many-to-many `role_user` table. The
   three roles are separate portals and nobody is both borrower and admin, so a pivot table
   would add joins with no benefit. The roles are inserted by their migration, not a seeder,
   because the app can't run without them and the test database must have them too.
3. **Contract terms as columns on `campaigns`, guarded by two-way CHECKs.** Each contract has
   its own nullable columns (`interest_rate_percent`; `markup_amount` and `asset_description`;
   `investor_profit_share_percent`). A CHECK makes each term *required* for its own contract
   and *NULL* for the others. *Alternative:* a separate table per contract type (PB-28/29).
   That is more normalised but needs a join for every campaign page, and the "no interest
   rate in Shariah mode" rule would then depend on application code. With the CHECK, MySQL
   itself refuses such a row, whatever code tries to write it. Shariah mode is not stored
   separately: it follows from `contract_type` (`Campaign::isShariah()`), so the two can never
   disagree.
4. **No predetermined return for Mudarabah.** In Mudarabah, investors' returns come from
   profit the business actually reports (PB-29). A fixed `return_due` on an instalment would
   be a guaranteed return, which Mudarabah prohibits, so the column is nullable and must be
   NULL for Mudarabah. A MySQL CHECK can only see the row being written, not
   `campaigns.contract_type` in another table, so this rule lives in the `RepaymentSchedule`
   model's `saving` event and is tested. *Alternative:* a MySQL trigger would enforce it in
   the database, but it hides logic outside the reviewed PHP code. *Limitation:* Eloquent
   events don't run for raw `DB::table()` writes, bulk `update()` queries or seeders using
   `WithoutModelEvents` (Laravel's default `DatabaseSeeder` does), so the code must not write
   instalments that way. For consistency the rule is two-way like the CHECKs: conventional and
   Murabahah instalments must state their `return_due`.
5. **Escrow is a wallet owned by the campaign.** `wallet_accounts` has a `type` (`user` or
   `escrow`) and exactly one owner, enforced by a CHECK. A pledge moves money from the
   investor's wallet to the campaign's escrow; a refund or disbursement moves it out. Money is
   only ever moved between wallets (except simulated top-ups and withdrawals), which lets PB-18
   prove the ledger reconciles. Both sides of a movement share a `transfer_ref` UUID.
6. **The database refuses a negative balance.** Each ledger row stores `balance_after`, with
   `CHECK (balance_after >= 0)`. PB-18's code must prevent it, but the database is the last
   line of defence. Every `return_payout` must reference both the investor's pledge and the
   repayment it came from (CHECK), so PB-36's pro-rata distribution is fully traceable.
7. **Encrypted national ID numbers.** `national_id_no` uses Laravel's `encrypted` cast
   (AES-256 with the app's `APP_KEY`), so a database dump does not expose ID numbers. The
   column is `text`, because the ciphertext (~200 characters) is longer than the ID. It is
   also `#[Hidden]`, so it never reaches a React page by accident. *Trade-off:* it can't be
   indexed, searched or made unique in SQL.
8. **All foreign keys `RESTRICT`.** Users are suspended, never deleted (PB-43), so financial,
   KYC and audit history can't disappear through a cascade. Deleting a user who has a
   campaign fails, and a test proves it.
9. **Notifications use Laravel's standard table.** Its `notifiable_type`/`notifiable_id` is
   polymorphic, so it has no database foreign key to `users`. In return, PB-39 gets
   `$user->notify()`, `unreadNotifications()` and the email channel for free. *Alternative:*
   a custom table with a real `user_id` foreign key, which would mean rebuilding those features.
10. **MySQL `ENUM` for status columns.** The database rejects an unknown status (strict mode
    reports "Data truncated"). Adding a new value later needs a small migration.
11. **Mass-assignment protection.** `role_id` and `status` are not in `User`'s `#[Fillable]`
    list, so a tampered registration request can't make itself a verified admin. Campaign
    status, KYC review fields and similar workflow fields are excluded in the same way.
12. **Money as `decimal(15,2)`**, cast to `decimal:2` (a string in PHP), never a float, so
    amounts don't pick up rounding errors.

## Sample code

The two-way contract CHECKs in `web/database/migrations/2026_11_11_000006_create_campaigns_table.php`.
Laravel's schema builder has no CHECK method, so they are added with SQL after the table is
created:

```php
DB::statement(<<<'SQL'
    ALTER TABLE campaigns
        ADD CONSTRAINT campaigns_conventional_terms_check CHECK (
            (contract_type = 'conventional'
                AND interest_rate_percent IS NOT NULL
                AND interest_rate_percent >= 0)
            OR (contract_type <> 'conventional' AND interest_rate_percent IS NULL)
        ),
        ADD CONSTRAINT campaigns_murabahah_terms_check CHECK (
            (contract_type = 'murabahah'
                AND markup_amount IS NOT NULL
                AND markup_amount >= 0
                AND asset_description IS NOT NULL)
            OR (contract_type <> 'murabahah'
                AND markup_amount IS NULL
                AND asset_description IS NULL)
        ),
        ADD CONSTRAINT campaigns_mudarabah_terms_check CHECK (
            (contract_type = 'mudarabah'
                AND investor_profit_share_percent IS NOT NULL
                AND investor_profit_share_percent > 0
                AND investor_profit_share_percent < 100)
            OR (contract_type <> 'mudarabah' AND investor_profit_share_percent IS NULL)
        )
    SQL);
```

And the rule MySQL can't express, in `web/app/Models/RepaymentSchedule.php`:

```php
protected static function booted(): void
{
    // "saving" runs before every insert and update made through Eloquent.
    static::saving(function (RepaymentSchedule $schedule) {
        $schedule->ensureReturnMatchesContract();
    });
}

public function ensureReturnMatchesContract(): void
{
    $contractType = $this->campaign()->value('contract_type');

    if ($contractType === Campaign::CONTRACT_MUDARABAH && $this->return_due !== null) {
        throw new ContractRuleViolation(
            'A Mudarabah instalment cannot have a predetermined return_due; '
            .'returns depend on the profit the business reports.'
        );
    }

    if ($contractType !== Campaign::CONTRACT_MUDARABAH && $this->return_due === null) {
        throw new ContractRuleViolation("A {$contractType} instalment must state its return_due.");
    }
}
```

keys and nullability are exactly what the migrations create. Sizes: VARCHAR/CHAR = maximum
characters; DECIMAL = precision,scale; integer types = maximum digits; ENUM, TIMESTAMP, DATE,
DATETIME and JSON have no size. Allowed ENUM values are listed in the description. CHECK
constraints are listed in [`docs/erd.md`](../erd.md#constraints-mermaid-cant-show).

## Checking that the tests can fail

On 11 Nov 2026 two rules were removed temporarily: the "NULL otherwise" half of
`campaigns_conventional_terms_check`, and the Mudarabah branch of
`RepaymentSchedule::ensureReturnMatchesContract()`. Exactly the five tests that guard them
failed (TC-05-16, TC-05-23, TC-05-30, TC-05-34, TC-05-35): `Tests: 98, Failures: 5`. Both
files were then restored and all 98 passed again. Nothing from this check was committed.
