# PB-57 – PB-59 Second usability round: polish, financial profile, legacy cleanup

Sprint 4 · 5 + 8 + 2 points · traces to the second usability test, FR1, FR8, IR 1.8.1, NFR
usability and accessibility · GitHub issues #69, #70, #71 (PB-60 #72 is planned for Sprint 5)

Built as one item: all three change the same onboarding wizard, profile model and seeders. PB-59
removes columns from the profiles PB-58 extends, the seeders are rewritten once for both, and
PB-57 restyles the inputs and warnings on the same pages. See `docs/decisions.md`, 23 Nov 2026.

Screenshots for the report are taken once in Sprint 5 (PB-56), so there are none here.

## What was built

### PB-57 UX polish

- **Band and pattern.** The sidebar band is one step more tinted and the background pattern is at
  10% (12% in dark) instead of 7% (9%), in all four themes. `npm run check:contrast` now reads the
  opacity from the theme instead of hard-coding it, and still passes: 340 pairs, none below AA
  (`text-muted` on the band is the closest at 4.51:1; text on the band itself uses
  `text-secondary`, 5.5:1 or more over the pattern).
- **Figures in inputs.** Every number input (money, percentages, counts) uses the figure font
  (IBM Plex Mono) with tabular digits: a `figures` option on `TextInput`, used by `MoneyInput`,
  `PercentInput` and the new `CountInput`. `MoneyInput` adds thousands separators while you type
  ("120,000") and keeps the cursor after the digit it was after; Backspace on a separator deletes
  the digit before it. The form still sends the plain number (120000).
- **Warnings where they matter.** The portal overview no longer shows "Your account is pending
  verification" or "Pledging is locked". The marketplace says why pledging is locked; the
  onboarding review step and the financing request pages already explain pending verification.
  The rejected and suspended notices stay on every page, as they block everything.
- **Address fields** no longer show example tips; the postcode keeps "5 digits".
- **Theme switch.** The three-way light / dark / system control became a minimal icon-only
  sliding switch: a sun and a moon on the track, the knob sliding between them over
  `duration-base` with `ease-standard`, and no movement with reduced motion. It is a
  `role="switch"` button named "Dark theme". In the collapsed sidebar it stands vertically.
- **The most recent change wins.** The user's choice is saved together with the device's setting
  at that moment (`users.theme`, `users.theme_system_at_choice`). With no choice the device
  decides. On the next load the choice is kept while the device still has the setting it had;
  if the device's setting has changed since, the device wins. While a page is open, a device
  change is followed at once. The rule is applied by the head script before the first paint and
  by `resolveTheme()` in the browser, so there is no flash.

### PB-58 Financial profile and salary verification

- **A "Finances" step in the onboarding wizard** (borrowers: details → address → finances →
  documents → review). It holds monthly income, monthly repayments on existing loans and cards,
  time in the job or business, housing, and the three credit-history answers that used to be on
  every financing request (PB-14). The administrator sees them on the verification record and
  checks them as part of KYC.
- **Monthly income, annual for the model.** Borrowers declare monthly income before tax (for an
  SME, the business's average monthly revenue). Annual income (× 12) is worked out only where the
  model needs it: `CampaignFinancials::annualIncome()`, used by `RiskFeatures`, and the Python
  side's `platform_features()`. The shared parity fixture now gives monthly income; its expected
  features are unchanged, and both the PHP and the Python test suites still match it.
- **The request form shows the profile read-only**, with "Update in your profile" (which brings
  the borrower back to the form if nothing changed). On submission the profile is copied into
  the request (`campaign_financials`, now storing monthly income), so each request keeps the
  figures it was made with even if the profile changes later.
- **Changing it sends the account back.** The finance step stays open after verification (every
  other step locks). If a verified borrower changes a value, the account goes back to pending and
  straight into the admin queue, and new requests are refused until it is approved again.
  Requests already made are untouched. A borrower verified before this change has no financial
  profile and must complete it before submitting a request.
- **Salary slip.** Individual borrowers have a third required document slot, "Salary slip" (the
  last 3 months; one PDF can hold several months), reviewed with the other documents. SMEs keep
  their financial statement.
- **Existing data** is migrated: monthly income = declared annual income ÷ 12, the other answers
  from the borrower's latest request; request snapshots convert annual to monthly. Every
  migration rolls back.

### PB-59 Remove legacy address handling

- A new migration drops `address_legacy` and `address_needs_review` from both profile tables (the
  PB-53 migration is left as it ran); its rollback puts them back. The best-guess parser
  (`LegacyAddress`), the "check your address" message, the "Address as first entered" row and
  their tests are gone; a complete address is now simply every field filled in.
- **Realistic demo data.** A shared `DemoData` seeder helper gives every demo account a Maldivian
  address from the island list, a financial profile for borrowers, and a small generated PDF in
  every document slot, marked "Demo document, not a real document", stored encrypted through
  `KycDocumentStore` so View works. `DatabaseSeeder` seeds an admin, a verified individual and a
  verified SME borrower, a verified investor, a borrower waiting in the queue and a new investor.
  The development database was rebuilt with `migrate:fresh --seed`.

## Design decisions and alternatives

- **Profile instead of per request.** Declared once and checked once by an administrator with
  evidence (salary slip, financial statement, credit report) is more trustworthy than figures
  retyped on each request. The snapshot keeps each request's risk score tied to what was true when
  it was made. Alternative: keep asking per request (no verification, repeated typing).
- **Back into verification on change.** Letting a verified borrower change verified income
  without a new check would make the check meaningless; locking the step would leave no way to
  update it. Re-verification with an automatic resubmission is the middle path.
- **Monthly income stored, annual calculated.** Salaries and slips in the Maldives are monthly, so
  that is what is typed and checked; the ×12 lives in one helper on each side and both parity
  suites cover it. Alternative: ask for annual income (harder to check against a slip).
- **Two-way theme switch with "most recent change wins".** It covers what "system" did without a
  third state: a choice holds until the device's setting changes. Alternative: keep three options
  (the usability test found them unclear).
- **Separators while typing.** Formatting on every keystroke usually makes the cursor jump; the
  helper counts digits, not characters, to put it back after the same digit. Alternative: format
  only on blur (the usability test asked for live grouping).
- **Real demo files, generated in code.** Factory rows without files made "View" fail in the
  demo; generating a marked PDF keeps binaries out of the repo and every value invented.

## Limitations

- **SME income versus the training data.** SME borrowers enter their business's average monthly
  revenue, while the model was trained on LendingClub borrowers' personal income. Revenue is
  usually far larger than an owner's income and is not net of business costs, so for SMEs the
  income-based features (loan-to-income, repayment burden, debt-to-income) will look smaller than
  for a comparable individual, and the risk score may understate risk. The ratios are shown to
  the administrator, and PB-21/PB-49 should evaluate SME requests separately (or ask for the
  owner's drawings as a second figure).
- **Rounding in rollback.** Converting annual to monthly income (÷ 12) and back can change an
  amount that wasn't a multiple of 12 by a few laari.
- **PB-53's address migration can no longer convert old single-line addresses**, because PB-59
  removed the parser. Fresh installs and CI are unaffected; every existing database had already
  run it.

## Sample code

The theme rule, shared by the first-paint script and the browser (`web/resources/js/lib/theme.js`):

```js
export function resolveTheme(saved, system) {
    const choice = THEMES.includes(saved?.choice) ? saved.choice : null;
    const atChoice = THEMES.includes(saved?.systemAtChoice) ? saved.systemAtChoice : null;

    if (choice === null) {
        return system;
    }
    return atChoice === null || atChoice === system ? choice : system;
}
```

A verified borrower's change sends the account back for checking
(`web/app/Http/Controllers/OnboardingController.php`):

```php
$profile->fill($request->financialData());
$changed = $profile->isDirty(BorrowerProfile::FINANCIAL_FIELDS);
$backToVerification = $changed && $user->status === 'verified';

DB::transaction(function () use ($user, $profile, $before, $backToVerification) {
    $profile->save();

    if ($backToVerification) {
        $user->status = 'pending_verification';
        $user->status_reason = null;
        $user->verification_submitted_at = now();
        $user->save();

        AuditLog::record('user.financial_profile_changed', $user, [
            'before' => $before,
            'after' => $profile->financialProfile(),
        ]);
    }
});
```
