# PB-13 – PB-15 Financing requests and campaign review

Sprint 2 · stories · 5 + 2 + 3 points · traces to FR10, FR8, IR 1.8.1, IR 1.8.3 · GitHub issues #13, #14, #15

Built as one item: the admin review (PB-15) has nothing to review until a borrower submits a
request (PB-13) with its financial information (PB-14), and PB-14's fields are sent on PB-13's
form in one transaction. See `docs/decisions.md`, 18 Nov 2026.

## What was built

- **Financing request (PB-13).** A verified borrower fills in one form:
  - title, purpose (start-up, growth, education or personal) and description, plus an
    optional business background;
  - amount (MVR 10,000 – 2,000,000) and tenure (3 – 60 months);
  - the contract: conventional, Murabahah or Mudarabah, picked with the new
    `ContractTypePicker`, and only that contract's own terms:
    - conventional: an interest rate;
    - Murabahah: the asset and a fixed markup, with the total sale price worked out live;
    - Mudarabah: the investors' share of the profit, with the share the business keeps.

  On submit, the request is saved as `submitted` with the time. Unverified borrowers see the
  reason instead of the form, and their POST is refused (403).
- **Shariah mode follows the contract.** Picking Murabahah or Mudarabah switches the whole page
  to the Shariah palette at once (the 500 ms cross-fade). After the request is saved, the server
  keeps the borrower in Shariah mode while their latest request is a Shariah contract.
- **Financial information (PB-14).** The same form collects every field in both deployable
  feature sets from PB-12:
  - annual income (pre-filled from the profile, stored per request);
  - monthly repayments on existing loans and cards, excluding housing;
  - years in the job or business;
  - housing (rent, own, own with a home loan, family home);
  - three self-declared credit-history answers: open loans and cards, 30+ day late payments
    in the past 2 years, and court judgments, bankruptcies or written-off debts.

  Every field is required. A missing or invalid one blocks submission, with a message under
  the field and a summary at the top.
- **MMA credit report (PB-14).** Optional. The upload has the same checks as a KYC document
  and is stored the same way: encrypted, a random name, a private disk, and opened only
  through `/documents/{id}` by the owner or an admin. It is linked to the request
  (`kyc_documents.campaign_id`).
- **`RiskFeatures`.** Turns a stored request into the 10 features of PB-12's
  "deployable + self-declared" set, with the same names, order and definitions as the Python
  training code. It is proved by a value-parity fixture read by both test suites.
- **Campaign review (PB-15).**
  - **Queue:** "To review" (oldest first) and "Live" (soonest deadline first).
  - **Review page:** the self-declared answers sit next to the attached credit report (or a
    note that none was attached). The page also shows:
    - the request and its contract terms;
    - the borrower's verification status;
    - their finances;
    - the three ratios the model will see;
    - a note when the tenure is outside the model's 36/60-month training range.
  - **Decisions:**
    - Approve: submitted → live, with a 30-day funding deadline.
    - Reject: submitted → rejected, with a required reason.
    - Suspend: live → suspended, with a required reason.

    Each decision is confirmed in a dialog, written in one transaction with a row lock,
    audited, and emailed and stored as an in-app notification after commit.
- **Marketplace, first version.** `/investor/campaigns` lists live campaigns whose deadline
  hasn't passed, closest deadline first, with the deadline and the days left. PB-16 adds
  search, filters and pages.
- **New components:** `MoneyInput`, `PercentInput`, `ContractTypePicker`, `ContractBadge`
  (names and props from `component-api.d.ts`). `Input` gained `controlClassName` and
  `Textarea` gained `optional`. All four new components are on `/dev/design`.
- **Portals:** the borrower home offers "New request" once verified, and the admin home counts
  requests waiting for review. The sidebars gained "Financing requests", "Marketplace" and
  "Campaigns".
- **Tests:**
  - 175 new PHP tests (554 in the web suite, up from 379);
  - 28 new Vitest tests (105);
  - 8 new pytest tests (94).

## Design decisions and alternatives

1. **Financial information in its own table.** `campaigns` holds the offer investors see;
   `campaign_financials` holds the facts the model uses.
   - Income is copied onto the request, so a later profile change can't change what a
     request was scored on.
   - *Alternative:* more columns on `campaigns`. That is simpler, but it mixes private
     financial facts into the table every marketplace query reads.
2. **The credit report reuses the KYC document store.** It gets the same encryption, private
   disk, random name and owner-or-admin route, so no new file code needs securing.
   - **Risk found and closed.** `VerificationService` approved or rejected *every* pending
     document a user had, so re-verifying an account would also have decided their credit
     report.
   - **The fix:** `User::kycDocuments()` now returns identity documents only, so every
     verification query (checklist, admin page, decision) leaves reports alone.
   - **Proof:** three tests failed with the fix removed and pass with it in place.
   - A CHECK constraint makes sure a report always belongs to a request and an ID document
     never does.
3. **One form, submitted in one go; no drafts.** No acceptance criterion needs drafts, and
   they would add a second, partial validation path. The `draft` status stays unused.
4. **Two-way contract rules in validation as well as the database.** Each term is
   `required_if` its contract and `prohibited_unless` its contract, so a Murabahah or
   Mudarabah sent with any rate, even 0%, is refused with a message before the PB-05 CHECK
   constraint would refuse it.
5. **Shariah wording lives in one place and is tested.** Everything the form says about
   contracts is in `lib/contracts.js`.
   - The contract cards stay on screen in Shariah mode, so their text never says "interest".
   - The rate field (which does) only appears while Conventional is picked, which puts the
     page in conventional mode.
   - Vitest checks every Shariah-visible string. PHP tests check the borrower and admin page
     props, the Shariah fields' messages and all six decision emails.
6. **Mode preview without an "undo on leave".** The first version put the old mode back when
   the form unmounted.
   - The end-to-end run caught a bug: the page transition keeps the old page mounted for its
     150 ms exit, so the "undo" landed *after* the next page's mode. A borrower who had just
     submitted a Murabahah was flipped back to conventional.
   - Now `ModeScope` re-applies the server's mode on every page change (keyed on the URL),
     and the form only previews.
7. **Value parity through one shared fixture.** The live model must receive the same numbers
   it was trained on, so the definitions in PHP and Python must agree.
   - Four applicants with hand-worked values sit in `risk-service/tests/fixtures/feature_parity.json`.
   - `RiskFeaturesTest` (PHP) and `test_feature_parity.py` (Python) both check against it.
   - They cover a 12-month and a 48-month tenure, the family home, zero debt, and 10+ years.
   - The same work changed `PLATFORM_PURPOSES` to the stored values (`start_up`, not
     `start-up`): the key-parity check would not have noticed that mismatch.
8. **Tenures 3 – 60 months, though LendingClub has only 36 and 60.** The form should fit
   Maldivian borrowers, not the dataset.
   - `RiskFeatures` sends any tenure as a plain number.
   - The admin page flags tenures other than 36/60.
   - PB-21 must treat `term_months` as numeric (noted on issue #21).
9. **A fixed 30-day deadline ending at midnight in the Maldives.** The server runs in UTC, so
   the deadline is stored as 18:59:59 UTC.
   - The server also sends the date as a Maldives label (`funding_deadline_label`), and pages
     show that, not the browser's own conversion of the time.
   - The end-to-end run found why this matters: on the developer's laptop (UTC+8) the
     marketplace showed 19 Dec while the approve dialog and the email said 18 Dec.
   - Counting days left still uses the exact time, so it is right in any time zone.
   - *Alternative considered:* the admin picks 14, 30 or 60 days.
10. **A minimal marketplace now.** It makes "appears in the marketplace with a funding
    deadline" demonstrable. PB-16 builds on the same `listed()` query.
11. **Investors don't see an individual borrower's name**, only an SME's business name. The
    marketplace props carry no borrower object and no rate.

## Sample code

`RiskFeatures::fromValues()`, the PHP half of the parity check. The Python half builds the same
values through `build_features()`, and both are tested against one JSON fixture:

```php
// web/app/Support/RiskFeatures.php
public static function fromValues(array $application): array
{
    $amount = (float) $application['amount_requested'];
    $tenure = (int) $application['tenure_months'];
    $monthlyIncome = (float) $application['annual_income'] / 12;

    return [
        'term_months' => $tenure,
        'purpose_group' => self::PURPOSE_GROUPS[$application['purpose']],
        'loan_to_income' => $amount / (float) $application['annual_income'],
        'repayment_burden' => ($amount / $tenure) / $monthlyIncome,
        // LendingClub's dti: monthly debt repayments (excluding housing and the new
        // request) as a percentage of monthly income.
        'dti' => (float) $application['monthly_debt_repayments'] / $monthlyIncome * 100,
        'emp_length_years' => min((int) $application['employment_years'], CampaignFinancials::MAX_EMPLOYMENT_YEARS),
        'home_ownership' => self::HOME_OWNERSHIP[$application['housing']],
        'open_acc' => (int) $application['open_credit_lines'],
        'delinq_2yrs' => (int) $application['late_payments_2y'],
        'pub_rec' => (int) $application['public_records'],
    ];
}
```

```python
# risk-service/tests/test_feature_parity.py
@pytest.mark.parametrize("applicant", APPLICANTS, ids=[a["name"] for a in APPLICANTS])
def test_platform_features_match_the_shared_fixture(applicant):
    row = d.platform_features([applicant["application"]], FIXTURE["feature_set"]).iloc[0]
    for name, expected in applicant["expected_features"].items():
        if isinstance(expected, str):
            assert row[name] == expected, name
        else:
            assert row[name] == pytest.approx(expected, abs=FIXTURE["tolerance"]), name
```

No contract term is an input, so a Murabahah and a conventional request with the same facts
get the same features: no interest rate can reach the model (TC-14-16).
