# PB-04 Continuous integration with GitHub Actions

Sprint 1 · chore · 2 points · traces to IR 3.1.3 (Definition of Done) · GitHub issue #4

## What was built

A GitHub Actions workflow that runs both automated test suites on a clean machine every time
code is pushed to any branch or a pull request is opened or updated:

- **One workflow, two jobs in parallel.** `Laravel tests (web)` and `pytest (risk-service)`.
  If either has a failing test, its job fails and the whole workflow shows red.
- **A real MySQL 8.4 database in CI.** The Laravel tests run against a MySQL *service
  container*, the same release as the local Homebrew `mysql@8.4`, so `DatabaseConnectionTest`
  (which rejects SQLite and MariaDB) passes in CI too.
- **The React/Tailwind assets are built in CI** (`npm run build`) before the tests run, so a
  front end that no longer compiles also fails CI.
- **A status badge** at the top of `README.md` showing the latest result on `main`.
- **PHP minimum corrected to 8.4.** While planning CI it turned out that `composer.lock` pins
  Symfony 8.1 components that need PHP ≥ 8.4.1, so the `^8.3` constraint in `composer.json`
  and "PHP 8.3+" in the READMEs were wrong: `composer install` fails on 8.3. Both were fixed;
  no package versions changed (only the lock file's hash and platform line).

Each run takes about one minute (web job ≈ 50–55 s, risk-service job ≈ 33–36 s).

## Design decisions and alternatives

1. **MySQL service container instead of SQLite in CI.** PB-02 decided that tests run on MySQL
   because the wallet ledger (PB-18) depends on MySQL behaviour that SQLite ignores (row
   locks with `lockForUpdate`, strict foreign keys, decimals). Switching to SQLite only in CI
   would mean CI tests a different engine from the one the app uses, and
   `DatabaseConnectionTest` would fail. A service container is a Docker container GitHub
   starts next to the job and deletes afterwards, so every run gets an empty database. A
   health check (`mysqladmin ping`) makes the job wait until MySQL accepts connections.
2. **How the app finds the database.** The container is created with the database name
   `phpunit.xml` already uses and a user for it. The job sets `DB_HOST`, `DB_USERNAME` and
   `DB_PASSWORD` as environment variables; Laravel reads `.env` without overwriting variables
   that already exist, so these win. No application or test code changed for CI.
3. **Password written in the workflow, not stored in GitHub Secrets.** It opens only a
   database that lives for about a minute on GitHub's machine and holds no real data, so it
   is not a secret. Secrets would add setup without adding security. Real credentials (none
   exist yet) would go in Secrets.
4. **Building the assets vs `withoutVite()`.** `@vite` in `app.blade.php` needs
   `public/build/manifest.json`, which is git-ignored. Calling `$this->withoutVite()` in
   `TestCase` would skip that, but CI would then never compile the React code. `npm run build`
   costs about 20 s and also catches a broken JSX import or Tailwind config.
5. **One workflow with two jobs vs two workflows.** One workflow gives one badge whose green
   means "both services pass", and the two jobs still report separately, so it is clear which
   side broke. The jobs share nothing, so they run at the same time.
6. **PHP 8.4 in CI.** It is the lowest version the locked packages support, so CI tests the
   minimum promised in `composer.json`, while the development machine runs PHP 8.5. Together
   they cover both. A matrix of 8.4 and 8.5 was considered but would double the web job for
   little gain in a single-developer project.
7. **Smaller choices.** Triggers are `push` (every branch) and `pull_request`; a
   `concurrency` group cancels a run when the same branch is pushed again. The workflow only
   gets `contents: read` permission (least privilege). Composer, npm and pip downloads are
   cached between runs, keyed on the lock/requirements files. The runner is pinned to
   `ubuntu-24.04` rather than `ubuntu-latest` so the environment does not change underneath
   the project mid-semester.

## Sample code

The part of `ci.yml` that gives the Laravel tests a database:

```yaml
# .github/workflows/ci.yml (web job)
services:
  mysql:
    image: mysql:8.4
    env:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: shariah_p2p_testing
      MYSQL_USER: shariah_p2p
      MYSQL_PASSWORD: ci-only-password
    ports:
      - 3306:3306
    # Do not start the steps until MySQL accepts connections.
    options: >-
      --health-cmd="mysqladmin ping -h 127.0.0.1"
      --health-interval=5s
      --health-timeout=5s
      --health-retries=20

# Real environment variables win over .env, so these point Laravel at the container.
env:
  DB_HOST: 127.0.0.1
  DB_PORT: 3306
  DB_USERNAME: shariah_p2p
  DB_PASSWORD: ci-only-password
```

The steps that follow, in order:

```yaml
- run: cp .env.example .env
- run: composer install --no-interaction --prefer-dist --no-progress
- run: php artisan key:generate      # APP_KEY, needed to encrypt cookies
- run: npm ci
- run: npm run build                 # public/build/manifest.json for @vite
- run: php artisan test
```
