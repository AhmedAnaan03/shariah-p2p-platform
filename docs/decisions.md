# Technical decisions

Record any change from the stack justified in the IR (Section 2.4), judged against the IR's
criteria: security, clean integration, developer skill level, cost.

| Date | Decision | Alternatives considered | Reason |
|---|---|---|---|
| 26 Oct 2026 | Sprint length cut from 2 weeks to ~9 days (5 sprints, 26 Oct – 9 Dec) | Keep 2-week sprints and drop scope; fewer, longer sprints | Final deadline is 16 Dec 2026 and all work should finish a week early for review. Same scope, shorter feedback loop; mention as an adaptation in Chapter 3. |
| 27 Oct 2026 | **React integration: Inertia.js** (PB-02). Laravel controllers return React pages via `Inertia::render()`; one app, one set of routes | Separate React SPA calling a Laravel JSON API (Sanctum); Blade with React "islands" | *Security:* keeps Laravel's session login and CSRF protection, with no API tokens, CORS or cross-origin cookie setup to get wrong. *Integration:* routing, authorisation and server-side validation stay in Laravel, and validation errors reach React forms automatically. Feature tests can assert which page and props a role receives, which the role-access tests need. *Skill/time:* one codebase and one test suite instead of two, which suits a solo developer on five ~9-day sprints. *Cost:* none. Trade-off: no public API for a mobile client, which is out of scope. The Flask risk service is unaffected (Laravel calls it server-to-server). |
| 27 Oct 2026 | No Laravel starter kit; Inertia + React added by hand, in JavaScript (JSX) rather than TypeScript (PB-02) | Official Laravel React starter kit (TypeScript, shadcn/ui, built-in auth) | The starter kit ships registration, login and password reset, which are backlog items PB-06–PB-08 with their own acceptance criteria and tests. Building them in-sprint keeps every line explainable in the viva. JSX avoids a type layer the developer would also have to explain. |
| 27 Oct 2026 | MySQL 8.4 LTS installed natively with Homebrew (`mysql@8.4`), not XAMPP (PB-02) | XAMPP; MySQL in Docker | Current XAMPP bundles MariaDB, not MySQL 8, which would quietly break the IR's MySQL 8 choice. 8.4 is the long-term-support release of MySQL 8. Native avoids keeping Docker running. A test (`DatabaseConnectionTest`) fails if the server is not MySQL 8. |
| 27 Oct 2026 | Tests run on a separate MySQL database (`shariah_p2p_testing`) instead of Laravel's default in-memory SQLite (PB-02) | SQLite `:memory:` (Laravel default) | The wallet ledger relies on MySQL behaviour that SQLite ignores or differs on (row locks via `lockForUpdate`, strict foreign keys, decimal handling). Tests should prove the real engine. Cost: slightly slower tests, and CI (PB-04) needs a MySQL service container. |
| 11 Nov 2026 | PB-06, PB-07 and PB-08 built as one item: one branch (`feature/PB-06-08-accounts`) and one PR closing all three | One branch and PR per item (the usual workflow) | The three stories are one account system: registration signs the user in and redirects to a role portal (PB-07), and all three share one password rule and one session. Built separately, each PR would need temporary stubs for the others. The PR has a section per item showing how each acceptance criterion is met, and commits keep their `PB-XX:` prefix so each story's work stays traceable. |
| 12 Nov 2026 | PB-09, PB-10 and PB-11 built as one item: one branch (`feature/PB-09-11-verification`) and one PR closing all three | One branch and PR per item | The admin queue (PB-11) has nothing to review until the borrower and investor profiles and documents (PB-09, PB-10) exist, and all three share one "ready for review" rule (`VerificationChecklist`) and one document store. The PR has a section per item, and commits keep their `PB-XX:` prefix. |
| 12 Nov 2026 | Shared React component library in `web/resources/js/components/` (Input, Select, Textarea, FileUpload, Checkbox, RadioGroup, Button, Alert, Badge, Card, layouts, ...); pages may not style their own controls (PB-09) | Keep styling each page by hand, as PB-06–08 did; a UI kit such as shadcn/ui or Headless UI | *Integration:* the PB-06–08 pages and every new page now share one look and one accessible label/hint/error pattern, so later sprints only assemble pages. *Skill:* small hand-written components in plain JSX with Tailwind, no new dependency to learn or explain. *Cost:* none. |
| 12 Nov 2026 | KYC upload limit 5 MB; the development `php.ini` raised to `upload_max_filesize = 10M`, `post_max_size = 12M` (PB-09) | Keep PHP's 2 MB default and a 2 MB app limit | Phone photos and scanned PDFs of ID cards often exceed 2 MB. PHP's limits are set above 5 MB so Laravel, not PHP, rejects a 5–10 MB file with the app's message. Documented in `web/README.md`; tests don't depend on `php.ini`. |
| 16 Nov 2026 | **Adopt the Amanah design system** (PB-51): Tailwind v4 tokens from `docs/design-system/`, platform-wide conventional / Shariah palette, self-hosted fonts (`@fontsource-variable/bricolage-grotesque`, `@fontsource-variable/figtree`, `@fontsource/ibm-plex-mono`), Radix primitives (`@radix-ui/react-*` ×12), Motion (`motion`) and Phosphor icons (`@phosphor-icons/react`); dev-only Vitest, puppeteer-core and axe-core. All pinned to exact versions | Keep the hand-styled components from PB-09; shadcn/ui; Headless UI; Google Fonts from a CDN | *Security:* fonts and icons are bundled, so the app loads nothing from third-party servers and the demo works offline. *Integration:* the theme is plain Tailwind v4 CSS (`@theme`), so no build change; Radix gives tested keyboard and screen-reader behaviour for dialogs, menus, selects and toasts, which hand-written versions would get wrong; the mode is one `data-mode` attribute, written by the server on first paint and shared as an Inertia prop. *Skill:* Radix and Motion are used through small wrapper components, so pages never touch them. shadcn/ui was rejected because the design system forbids its default look. *Cost:* free; the JS bundle grows from 117 kB to 258 kB gzipped (code-splitting is possible later). Vitest tests the JS helpers the PHP tests can't reach; puppeteer-core drives the installed Chrome for screenshots and axe-core audits the rendered pages for WCAG 2.2 AA. |
| 16 Nov 2026 | Shariah-only switch disabled until the investor's profile exists (PB-51) | Move `shariah_only` from `investor_profiles` to `users` | The preference already lives on the profile (PB-05 ERD), whose phone, ID and address columns are required, so there is nowhere to store it before the profile is saved. Disabling the switch with an explanation keeps the data model unchanged; the PATCH route also refuses with a clear message. |
| 18 Nov 2026 | **Training data: LendingClub accepted loans 2007–2018** (Kaggle `wordsforthewise/lending-club`, CC0), restricted to individual loans from matured cohorts: 777,399 loans, 15.19% default (PB-12) | Home Credit Default Risk; German Credit (UCI); Give Me Some Credit; US SBA 7(a) loans; all finished LendingClub loans without the maturity filter | Real peer-to-peer lending with a real default outcome, enough loans for CV and SMOTE, and fields for all four IR feature groups. Home Credit's competition licence forbids reuse; German Credit is tiny and has age and sex built in; Give Me Some Credit has no application fields; SBA has no borrower capacity or history. The maturity filter (term ended by the Mar 2019 snapshot) removes the bias where recent loans only appear finished if they defaulted or paid off early. Limitation: US consumer data in USD, so PB-49 covers recalibration on local data. |
| 18 Nov 2026 | **Two feature sets** (PB-12; superseded the same day by the three-set row below): *deployable* (7 features our PB-13/PB-14 form can collect: term, purpose group, loan-to-income, repayment burden, DTI, employment length, home ownership) is the only set the production model may use; *full* (adds 8 credit-bureau features such as FICO, delinquencies, enquiries, revolving utilisation) is trained in PB-21 only as a benchmark | One set with bureau fields (borrowers would have to supply FICO-like data that does not exist in the Maldives); one deployable set only (no evidence of what is lost) | Maldivian borrowers have no FICO score, and the MMA Credit Information System self-inquiry report gives only partial history that an admin would have to type in, so a production model needing bureau fields could not score real applicants. Training the full set as well measures the accuracy cost of that constraint for Chapter 5. The full set excludes bureau fields LendingClub only began in 2012/2015, so the gap it shows is a lower bound. |
| 18 Nov 2026 | `pyarrow` added to the runtime requirements; a separate `requirements-notebook.txt` (kaggle CLI, JupyterLab, ipykernel, nbconvert, matplotlib) for the dataset download and exploration notebook (PB-12) | Read the CSV with pandas each time; put the notebook tools in `requirements-dev.txt` | The 1.6 GB CSV with 151 columns does not fit in an 8 GB laptop's memory when read in one go and takes minutes to parse. `ml.prepare` converts it once to Parquet (302 MB), and later reads load only the needed columns in seconds; the training pipeline (PB-21) reads the same file, so pyarrow is a runtime dependency. The notebook tools are only needed by the developer, so CI (`requirements-dev.txt`) stays lean. All pinned to exact versions. |
| 18 Nov 2026 | **Three feature sets instead of two** (PB-12, replaces the "two feature sets" row above): *deployable* (7), *deployable + self-declared history* (10: adds `open_acc`, `delinq_2yrs`, `pub_rec`) and *full* (15, benchmark). PB-21 trains all three and picks the production set from the results | Keep two sets with the deployable set fixed as production; put all bureau fields in the self-declared set | A borrower can state how many loans and cards they have open, how often they were 30+ days late in the past 2 years, and whether they have judgments, bankruptcy or written-off debts, and an admin can check those answers against the MMA Credit Information System report the borrower uploads. That fills the IR's credit-history group, which the deployable set leaves empty. FICO, enquiries, total accounts, utilisation and history length stay benchmark-only: there is no Maldivian score, and the rest cannot be reliably checked from the report. Risks recorded for PB-21: the three answers are individually weak (AUC 0.507–0.513), and self-reported values may be less accurate than the bureau values the model learned from. Auto-filling them from the report is PB-52. |
